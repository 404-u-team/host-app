# Host App Desktop

Простой настольный клиент JavaFX для существующего Host App backend. CLI и backend остаются отдельными проектами. API-классы и DTO скопированы из CLI в пакет `dev.hostapp.desktop`, общей клиентской библиотеки нет.

## Требования и запуск

Нужны JDK 17 или новее, Maven 3.9 или новее и Docker Compose для backend и PostgreSQL. Можно использовать JDK 21, указанный в задании. Код компилируется под Java 17, как существующие части проекта. JavaFX 21.0.8 Maven загружает самостоятельно, отдельный JavaFX SDK и Scene Builder не нужны.

Из корня проекта запустите backend и базу:

```sh
cd host-app-backend
docker compose up --build
```

Проверка: `http://localhost:8080/health` должен вернуть `OK`.

В другом терминале из корня проекта:

```sh
cd host-app-desktop
mvn javafx:run
```

Если backend работает по другому адресу:

```sh
mvn -Dhostapp.api=http://127.0.0.1:8081 javafx:run
```

У нашего API нет общего префикса `/api`: указывайте только адрес и порт. JavaFX запускается на компьютере отдельно от Docker.

Если IDE выбрала другую Java, настройте JDK проекта и JDK Maven на одну установленную версию. На Linux для одного запуска можно указать путь к JDK явно:

```sh
JAVA_HOME=/usr/lib/jvm/java-17-openjdk mvn javafx:run
```

## Что доступно

- Регистрация, вход и выход из аккаунта.
- Таблица заявок, просмотр подробностей, создание, изменение и удаление с подтверждением.
- Поиск по ОС, статусу и значениям ресурсов.
- Совместные фильтры по статусу, ОС и минимальному CPU. Кнопки «Применить» и «Сбросить» управляют фильтрами.
- Сортировка по заголовкам столбцов. CPU, RAM и диск сортируются как числа, даты по времени. Повторное нажатие меняет направление; Shift позволяет добавить ещё один столбец сортировки.
- Просмотр связанного сервера из выбранной заявки, без ручного ввода ID.
- Таблица серверов и их подробности. Администратор может изменять и удалять серверы.
- Шесть показателей статистики: всего, создано, одобрено, выполнено, отклонено, отменено. Статистика учитывает все доступные пользователю заявки, а не фильтр таблицы.
- CSV-экспорт текущей таблицы заявок с учётом поиска, фильтров и порядка сортировки. Файл выбирается через FileChooser. Кодировка UTF-8 с BOM, разделитель: точка с запятой.

Логин администратора: `ADMIN`. На пустой базе задайте `ADMIN_BOOTSTRAP_PASSWORD`
в окружении backend (12–255 символов) и запустите его: аккаунт создастся без письма.
В клиенте используйте вход с логином `ADMIN` и заданным паролем.
Повторный запуск не меняет существующего администратора; готового пароля по умолчанию нет.

Редактируется только заявка в статусе `CREATED`. Выполненную заявку удалить отдельно нельзя. Администратор может выполнить, отклонить или отменить созданную заявку. При выполнении backend создаёт запись сервера с её характеристиками. Статус `APPROVED` есть в модели, но сейчас не используется при создании новых заявок.

Удаление сервера удаляет и связанные заявки. Перед этим интерфейс показывает отдельное подтверждение. Запуск настоящих виртуальных машин, оплата, остановка и перезапуск серверов не реализованы в нашем backend.

## Структура

```text
src/main/java/dev/hostapp/desktop/
├── App.java
├── api/
├── dto/
├── controller/
├── service/
└── util/

src/main/resources/dev/hostapp/desktop/
├── login.fxml
├── register.fxml
├── main.fxml
├── requests.fxml
├── request-form.fxml
├── servers.fxml
├── server-form.fxml
├── statistics.fxml
└── style.css
```

`App` создаёт объекты и открывает экраны по явным путям ресурсов. FXML задаёт расположение элементов. Контроллеры получают действия пользователя и обновляют интерфейс. Сервисы проверяют ввод и правила операций. Классы API отправляют HTTP-запросы, DTO описывают их данные. Backend проверяет права и сохраняет изменения в PostgreSQL.

Таблицы используют `ObservableList`: после загрузки и изменения данных список заменяется через `setAll`. Поиск и фильтры применяются локально к уже загруженным доступным заявкам, сортировка выполняется средствами `TableView`. Для учебного объёма данных это позволяет обойтись без нового API и пагинации.

`BaseController` запускает сетевые обращения и запись файла через `Task` в отдельном потоке. Пока выполняется операция, интерфейс блокирует повторные действия. Обновление элементов происходит в обработчиках завершения задачи в потоке JavaFX. Таймаут подключения: 5 секунд, запроса: 20 секунд.

Cookies сессии хранятся только в памяти одного клиента. При выходе они удаляются. На ответ `401` после входа клиент возвращает форму авторизации. Серверного отзыва сессии при выходе нет, поскольку соответствующего endpoint в backend пока нет.

## Соответствие заданию

По выбранному для этого проекта варианту клиент работает через наш REST backend и предметную область заявок на серверы. Прямого подключения JavaFX через JDBC нет. Это сознательное отличие от приложенного задания КР2, где отдельное JDBC-подключение указано обязательным. Клиентскую роль DAO выполняют API-классы, а доступ к PostgreSQL остаётся в backend.

Приложение использует FXML, CSS, TableView, ObservableList, диалоговые формы, подтверждения удаления, проверку ввода, поиск, фильтры, сортировку, связанные данные, статистику и экспорт. Уникальность логина и имени сервера окончательно проверяет backend и база; ошибки возвращаются в диалог.

## Проверка

```sh
mvn test
mvn clean package
```

Автоматические тесты проверяют валидацию, совместное применение фильтров, переходы статусов, CSV и обмен с локальным тестовым HTTP-сервером, включая cookies и обработку ошибок. Для тестов API должна быть разрешена работа с локальными сетевыми портами. Docker, PostgreSQL и графический экран для `mvn test` не нужны.

Для ручной демонстрации на отдельной тестовой базе:

1. Зарегистрируйте пользователя и создайте заявку с CPU, RAM, диском и ОС.
2. Измените её параметры. Проверьте поиск, фильтры и сортировку; сохраните CSV.
3. Создайте вторую заявку и удалите её с подтверждением.
4. Создайте администратора через `ADMIN_BOOTSTRAP_PASSWORD` в окружении backend, выйдите из клиента и войдите с логином `ADMIN`.
5. Выполните заявку пользователя и откройте связанный сервер.
6. Измените имя, ресурсы и IP-адреса сервера. Проверьте статистику.
7. Войдите пользователем и убедитесь, что сервер доступен для просмотра, а действия администратора скрыты.
8. Проверьте пустые поля, нулевые и нечисловые ресурсы, неправильные IP-адреса, неверный пароль и недоступный backend.
