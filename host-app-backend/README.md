## Запуск всего backend через Docker Compose

Из каталога `host-app-backend`:

```sh
docker compose up --build
```

Команда собирает backend-образ, запускает PostgreSQL и ждёт готовности базы перед запуском приложения.
Swagger UI: http://localhost:8080/swagger-ui.html

Параметры можно переопределить переменными окружения или в `.env`: `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_PORT` и `BACKEND_PORT`. Значения по умолчанию предназначены для локальной разработки.

Для локальной разработки с запуском приложения через Maven поднимите только PostgreSQL:

```
docker compose -f docker-compose.dev.yaml up -d
./mvnw spring-boot:run
```

Требуется JDK 17 и Maven (для локального запуска; в Docker используются готовые образы Java и Maven).

## Email и SMTP

Скопируйте `.env.example` в `.env` и заполните параметры. Docker Compose передаёт их бэкенду.
При запуске через Maven переменные нужно экспортировать в окружение процесса: сам Spring Boot файл `.env` не читает.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `EMAIL_VERIFICATION_ENABLED` | `false` | Требовать подтверждение даже без автодетектирования SMTP; без SMTP запуск завершится ошибкой |
| `EMAIL_NOTIFICATIONS_ENABLED` | `true` | Письма владельцу при изменении статуса заявки |
| `SMTP_HOST` | пусто | Адрес SMTP-сервера |
| `SMTP_PORT` | `587` | Порт SMTP |
| `SMTP_USERNAME` / `SMTP_PASSWORD` | пусто | Учётные данные SMTP |
| `SMTP_FROM` | пусто | Email отправителя, разрешённый SMTP-провайдером |
| `SMTP_AUTH` | `true` | Авторизация; `false` для SMTP без учётных данных |
| `SMTP_SSL_ENABLED` | `false` | Неявный SSL, обычно порт 465 |
| `SMTP_TLS_ENABLED` | `true` | Обязательный STARTTLS, обычно порт 587 |

Если SMTP полностью отсутствует и `EMAIL_VERIFICATION_ENABLED=false`, регистрация проверяет email по regex и сразу разрешает вход.
Если SMTP настроен, подтверждение включается автоматически, в том числе при `EMAIL_VERIFICATION_ENABLED=false`.
Частично заполненная конфигурация считается ошибкой запуска. Для SMTP с авторизацией обязательны host, from, username и password;
при `SMTP_AUTH=false` достаточно host и from. SSL и STARTTLS одновременно включать нельзя.
Для SSL установите `SMTP_PORT=465`, `SMTP_SSL_ENABLED=true`, `SMTP_TLS_ENABLED=false`;
для STARTTLS — `SMTP_PORT=587`, `SMTP_SSL_ENABLED=false`, `SMTP_TLS_ENABLED=true`.
Оба режима можно отключить для локального тестового SMTP. Проверка сертификатов и имени сервера сохраняется.

### Подтверждение регистрации

1. `POST /auth/register` с `name`, `surname`, `email`, `password` возвращает существующие поля пользователя и `verificationRequired`.
2. Если `verificationRequired=true`, на email отправлен шестизначный код; вход до подтверждения запрещён.
3. `POST /auth/verify-email` с `email` и `code` подтверждает адрес и возвращает `verificationRequired=false`.
4. `POST /auth/resend-email-code` с `email` и исходным `password` отправляет новый код, не чаще раза в 60 секунд.

Код действует 10 минут, допускает 5 попыток и используется один раз. Повторная отправка аннулирует предыдущий код.
Коды хранятся в БД только как Argon2-хеши и не попадают в ответы API или логи.
Ошибка SMTP при регистрации возвращает HTTP 503 и откатывает создание аккаунта; ошибка повторной отправки сохраняет прежний код.
Для продолжения незавершённой регистрации снова отправьте те же email и пароль в `/auth/register`:
это откроет ввод кода без смены пароля и без автоматической повторной отправки письма.
Desktop и CLI поддерживают ввод и повторную отправку кода.

Существующие аккаунты сохраняют доступ: новая колонка `email_verified` получает значение `true` при обновлении схемы Hibernate.
Новые регистрации требуют корректный email; существующий служебный логин `ADMIN` по-прежнему работает при входе.

### Уведомления о заявках

После успешного сохранения нового статуса владелец получает письмо с ID заявки и старым/новым статусом.
Письма отправляются только при настроенном SMTP и `EMAIL_NOTIFICATIONS_ENABLED=true`, на подтверждённый email.
При откате транзакции письмо не отправляется. Ошибка доставки фиксируется в логе и не отменяет изменение статуса.
Автоматических повторных попыток доставки уведомлений пока нет.

## Флоу

### Создаение аккаунта

1. юзер заходит на главный экран
2. переходит на форму регистрации
3. регистрирует аккаунт
4. при настроенном SMTP подтверждает email кодом из письма
5. переходит на форму логина и входит
6. становится авторизованным

### Вход 

1. переход на страницу входа
2. ввод логин пароль
3. токен в куки задает бэкенд (httpOnly cookie)
4. юзер авторизован

> Вообще в моей идее изначально было так, что мы не даем проходить регистрацию/вход через CLI а даем только вставить токен, который можно создать на сайте

### Создание заявки

1. Переходим в форму создания
2. вводим желаемые параметры
3. отправляем заявку
4. заявка появляется в списке заявок

### Управление заявкой (администратор)

1. переходим в панель управления
2. переходим в список заявок
3. выбираем заявку
4. можем управлять статусом заявки и изменять параметры
5. при переходе из CREATED в COMPLETED создается сервер для владельца с характеристиками заявки (CPU, RAM, диск, ОС); APPROVED пока не используется

### Просмотр сервера (юзер)

1. переходим в личный кабинет
2. переходим в список серверов
3. выбираем нужный сервер из списка
4. попадаем на страницу сервера (доступные действия с сервером: продлить сервер(типа оплата), изменение сервера(новая заявка), отмена сервера(удаление), запуск сервера, остаеновка сервера, перезапуск)

### Просмотр заявок (юзер)

1. переходим в лк
2. переходим в список заявок
3. выбирем заявок из списка
4. попадаем на страницу заявки (доступные действия с заякой: изменение, отмена)
