# Как Host App прогнозирует количество новых заявок

## Что прогнозируем

Прогноз отвечает на один вопрос. Сколько заявок типа `CREATE` поступит завтра? Это прогноз потока новых заявок на создание серверов. Каждая заявка даёт один голос в день создания, независимо от текущего статуса. Заявки `CHANGE` и `CANCEL` в расчёте отсутствуют.

Даты и границы дня определяются настройкой `FORECAST_TIMEZONE`. По умолчанию используется `Europe/Istanbul`. В ответе API часовой пояс возвращается в поле `timezone`. Из реальных данных берём до 180 последних полных дней. Источник — события `SERVER_CREATE_REQUEST` в журнале аудита. Событие записывается в одной транзакции с созданием заявки, в том числе при импорте CSV. При установке Flyway формирует такие события для существующих заявок из их `created_at`. История сохраняется после архивирования и окончательного удаления заявки. Если запись была удалена ещё до установки Flyway, её исходную дату восстановить уже нельзя.

Ряд начинается с первого события в пределах выбранного диапазона. Дни между событиями и до вчера включительно заполняются нулями. Это допущение работает, пока по всем дням ведётся журнал. Если после заполнения ряда получается меньше 35 полных дней или все значения нулевые, API возвращает `INSUFFICIENT_DATA`. Сегодняшний неполный день из истории исключён.

## Что означает «рекуррентная»

У модели один вход на шаг. Это количество заявок за день. У неё также есть четыре внутренних числа, вместе они образуют **скрытое состояние**. Сеть обрабатывает дни последовательно, каждый раз используя количество заявок за следующий день и предыдущее состояние. Последнее состояние используется для прогноза.

Например, ряды `2 → 4 → 6 → 8` и `14 → 12 → 10 → 8` заканчиваются одинаковым числом. У сети есть возможность выдавать разные прогнозы: к последней восьмёрке она приходит с разным скрытым состоянием. Как именно реагировать на такую последовательность, определяют веса, найденные при обучении.

Наша реализация использует простую RNN Эльмана. Для одного окна из 14 дней обозначим через `x[t]` нормализованное число заявок за день `t`, через `h[t]` — четыре компоненты скрытого состояния. В начале окна `h[0]` состоит из нулей. Каждый шаг вычисляется так:

```text
h[t] = tanh(Wx * x[t] + Wh * h[t-1] + b)
y    = Wy * h[14] + by
```

Векторы `Wx`, `b` и `Wy` содержат по четыре числа. Матрица `Wh` имеет размер 4 × 4, `by` — одно число. Всего 29 обучаемых параметров. Одни и те же веса используются для каждого дня и каждого окна. Функция `tanh` поэлементно преобразует сумму в число между −1 и 1. Линейный выход `y` — прогноз следующего дня в нормализованном масштабе.

Для сравнения, если в ряду максимум обучающей части был 20, день с 10 заявками передаётся в сеть как 0,5. Выход 0,6 после умножения на 20 даёт 12 заявок. Масштаб берётся только из обучающей части, с минимумом 1. При оценке отрицательные прогнозы ограничиваются нулём, а округление выполняется только для итогового числа в API.

## Как модель учится

1. Историю делим по времени. Первые 80% дней идут на обучение, остальные используются для проверки. Будущие относительно обучения значения не участвуют в расчёте масштаба и подборе весов.
2. Из обучающей части последовательно берём окна. Если первые 15 значений имеют индексы 0–14, входом будут дни 0–13, ответом — день 14. Следующая пара использует дни 1–14 и ответ из дня 15.
3. Веса сначала небольшие случайные, с фиксированным seed 42. Для окна вычисляем скрытые состояния и прогноз. Потеря на окне равна половине квадрата ошибки `0.5 * (y - target)^2`.
4. По этой ошибке вычисляем производные выхода, затем возвращаемся от дня 14 к дню 1. Через цепочку состояний ошибка влияет на веса даже ранних шагов. Это **backpropagation through time**, или BPTT. Производная `tanh` выражается через сохранённое состояние как `1 - h[t]^2`. При обратном ходе градиенты общих весов суммируются по шагам окна.
5. После одного окна обновляем все параметры градиентным спуском. Градиент каждого параметра ограничиваем интервалом от −1 до 1, затем умножаем на шаг 0,025 и вычитаем из веса. Повторяем проход по обучающим окнам 80 раз. Один такой проход называется эпохой.

### Что точно происходит при обратном проходе

Если прогноз на окне вышел 0,6, а известное значение после нормализации — 0,8, производная потери по прогнозу равна `e = 0,6 - 0,8 = -0,2`. Производная по смещению выхода тоже равна `e`. По каждому элементу выходного вектора весов она равна `e * h[14]`. Чтобы найти вклад в ошибку от каждого компонента последнего скрытого состояния, умножаем `e` на соответствующий выходной вес.

Для каждого шага от 14 до 1 внутри сети происходит следующее:

```text
delta[t] = gradient(h[t]) * (1 - h[t]^2)
gradient(Wx) += delta[t] * x[t]
gradient(Wh) += delta[t] × transpose(h[t-1])
gradient(b)  += delta[t]
gradient(h[t-1]) = transpose(Wh) × delta[t]
```

В первой строке умножение поэлементное. В строке для `Wh` внешнее произведение двух векторов даёт матрицу 4 × 4. В коде это два вложенных цикла по текущему и предыдущему скрытым элементам. Знаки производных указывают, в какую сторону менять конкретный вес. Веса меняются после завершения обратного прохода, поэтому на всех шагах одного окна используются те же значения, что и при прямом проходе. При переходе к следующему окну скрытое состояние снова начинается с нулей, а обученные веса сохраняются.

Модель пересчитывается при запросе. При той же истории и том же начальном seed получаем тот же результат. Для учебного объёма расчёт ограничен четырьмя состояниями, 14 шагами окна и максимум 180 днями. Веса хранятся в памяти в течение запроса. Для обучения и прогноза достаточно Java и обычных массивов.

## Как получаем прогноз именно на завтра

Последний известный полный день — вчера. Нейросеть обучена прогнозировать один шаг, поэтому вызываем её дважды:

```text
14 дней до вчера включительно → прогноз на сегодня
13 последних известных дней + прогноз на сегодня → прогноз на завтра
```

Вторая строка использует число, рассчитанное на первом шаге. Если сегодня оценено неточно, эта ошибка может повлиять и на завтра.

Историческую проверку проводим с тем же горизонтом в два дня. Для каждого подходящего окна сначала получаем промежуточный прогноз, затем сравниваем второй прогноз с реально наблюдавшимся числом заявок. Среднее абсолютных отклонений — **MAE**, в заявках. Например, ошибки в 3, 2 и 1 заявку дают MAE ровно 2. В API есть `modelMae` для RNN и `baselineMae` для среднего за семь известных дней. Меньший MAE означает меньшую среднюю ошибку на этом отложенном периоде. Сравнивать нужно оба числа. На редких или резко меняющихся данных простое среднее может сработать точнее.

Код модели находится в `host-app-backend/src/main/java/dev/hostapp/backend/service/forecast/RequestRnn.java`. В методе `states` идёт прямой расчёт, в `trainWindow` — обратный проход и обновление весов, а `twoDaysAhead` дважды применяет прогноз. `ForecastService` строит даты и ряд, вызывает обучение и считает MAE.

## Как подготовить прошлые дни для защиты

1. В корневом `.env` выставить `FORECAST_DEMO_ENABLED=true` и пересоздать контейнер бэкенда через `host-app-backend/start-compose.ps1` или команду Compose из README.
2. Войти администратором через `POST /api/auth/login`. При первом входе сменить временный пароль через `POST /api/auth/change-password` и взять новый `accessToken` из ответа.
3. Выполнить `POST /api/analytics/request-forecast/demo-data` с заголовком `Authorization: Bearer <accessToken>`. Запрос без тела. Он записывает 120 полных дней до вчера включительно и возвращает диапазон дат, число дней и число добавленных записей. Повторный вызов в тот же день возвращает `inserted: 0`.
4. Вызвать `GET /api/analytics/request-forecast?source=DEMO` с тем же заголовком. В ответе есть `date`, `expectedRequests`, `recentHistory`, `modelMae`, `baselineMae`.
5. Вызвать `GET /api/analytics/request-forecast?source=REAL` для прогноза по рабочим данным. На свежей базе ожидаем `INSUFFICIENT_DATA`.

В режиме DEMO числа строятся по дню недели с небольшими воспроизводимыми колебаниями. Например, понедельник и вторник обычно загруженнее выходных. Они сохраняются в отдельной таблице `forecast_demo_days`. Поэтому учебные данные не создают учётные записи, заявки и серверы, не отправляют письма и не меняют рабочие отчёты. Запрос подготовки данных записывает в аудит одно событие о запуске демо. Функция по умолчанию выключена. Доступ к прогнозу и подготовке истории есть у администратора.
